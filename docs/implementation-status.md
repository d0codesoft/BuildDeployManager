# Отчёт о реализации SCODE Build & Deploy Manager

Реализована версия 0.1.0 по этапам `task.md`. Production SCLOUD не подключался и не изменялся. Готовность к конкретному production-развёртыванию требует приёмки на Ubuntu и проверки реальной инфраструктуры; локальный успешный pytest не заменяет эти проверки.

Основной сценарий изменён по уточнению: `deploy PROJECT --approve` сам сравнивает HEAD Git/GitHub с установленным commit, получает чистый checkout конкретного SHA, локально выполняет build/test/publish и меняет релиз после проверки. При совпадении commit clone/build/publish и перезапуск служб пропускаются. `--force` пересобирает даже текущий commit. Готовые подписанные архивы и внешние источники остаются дополнительными вариантами. Локальный артефакт проверяется по успешной записи сборки, полному manifest и SHA-256; ключ подписи для этого сценария не требуется. Автоматический rollback также проверяет сохранённую локальную сборку по журналу.

Основной код находится в `src/scdeploy/`; конфигурации — `projects/examples/`; установочные и административные операции — `scripts/`; планировщик — `systemd/`; автоматические проверки — `tests/`; документация — `docs/`. Исходный `task.md` сохранён. Примеры с литералами секретов очищены; реальный отзыв/замена старых учётных данных остаётся административной операцией. Демонстрационный SMTP-тест больше не отправляет письмо при импорте.

## Проверено локально

- Python 3.12.10, Windows, pytest: **94 passed, 3 skipped**. Добавлены проверки полной Git-цепочки, пропуска текущего commit, нового commit, --force, неудачной сборки, подмены локального артефакта, локального rollback, автоматической политики и конкурентного изменения установленной версии.
- Проверены все пять независимых YAML-конфигураций и CLI dry-run SCLOUD без создания состояния/логов.
- Собран wheel `scdeploy-0.1.0-py3-none-any.whl`; проверены импорт CLI из wheel, версия и entry point. Legacy example не включён в пакет.
- `compileall` прошёл для основного кода и Python-скриптов.
- Ошибки внешних уведомлений не меняют успешный результат основной операции.

Три пропуска: реальный локальный Git transport, заблокированный Windows-песочницей при запуске Git/MSYS; настоящее атомарное symlink-переключение; Unix-проверка symlink-предка. В Windows тесты транзакций явно используют адаптер символической ссылки и фиктивные службы. На Ubuntu адаптер отключён, используются настоящие файловые symlink; реальные службы проверяет отдельный E2E.

## Не проверено в текущей среде

- Установка на чистую Ubuntu 24.04, синтаксическая проверка Bash и реальные systemd/sudoers/Unix-права: WSL и Git Bash недоступны из-за ограничений песочницы.
- Настоящие .NET 8/9/10, npm и Python wheel/sdist сборки сторонних проектов: проведены проверки команд и обработки отказов, а не загрузка/компиляция их реальных зависимостей.
- Работа с реальными приватными GitHub-репозиториями, Actions/Releases, updates.example.com, SMTP и Telegram; внешние интеграции протестированы с подменой транспорта.
- Production layout SCLOUD, восстановление его БД, Nginx/wiki и старой версии: доступа к серверу нет.

Для подтверждения Ubuntu-приёмки предусмотрены `.github/workflows/tests.yml` и явно запускаемый сценарий `tests/ubuntu-e2e.sh`. Он предназначен только для одноразовой VM с настоящим systemd и проверяет установку подписанного первого релиза, отказ следующей версии и восстановление работающего процесса:

```bash
sudo bash tests/ubuntu-e2e.sh --isolated-vm --approve
```

## Установка и использование

```bash
sudo apt-get install python3 python3-venv python3-pip sudo util-linux
sudo bash scripts/install.sh
sudo -u scdeploy scdeploy doctor --json
sudo install -o root -g scdeploy -m 0640 projects/examples/example-node.yaml /etc/scdeploy/projects/example-node.yaml
sudo -u scdeploy scdeploy validate example-node
```

Затем администратор задаёт реальный репозиторий, каталог публикации, ключ доверия и службу. Для нового отсутствующего каталога приложения используется `scripts/provision-project.py`. Готовая служба должна работать от непривилегированного пользователя и ссылаться на `current`. Только после проверки окружения `observe_only` переключается в false.

Команды CLI: list, show, validate, check, fetch, build, test, artifacts, deploy, status, health, releases, rollback, history, logs, doctor, check-all, recover, import-legacy. Поддерживаются dry-run, JSON, версия/commit/artifact, approve, force, no-notify, signing-key и переопределение каталогов. Для Git-проекта deploy запускает всю локальную цепочку без --artifact; автоматическое развёртывание требует отдельной разрешающей политики и подтверждения происхождения локальной сборкой либо подписью внешнего артефакта.

```bash
sudo -u scdeploy scdeploy deploy PROJECT --approve
sudo -u scdeploy scdeploy deploy PROJECT --approve --force
sudo -u scdeploy scdeploy deploy PROJECT --artifact /safe/signed.tar.gz --approve
sudo -u scdeploy scdeploy rollback PROJECT --approve
sudo -u scdeploy scdeploy rollback PROJECT --version 1.4.1 --approve
sudo -u scdeploy scdeploy recover PROJECT --approve
```

Для SCLOUD сначала выполнить read-only `import-legacy`, подтвердить настоящую службу и пути, сделать независимые резервные копии и репетицию на VM. Ручной переход и восстановление описаны в `migration-scloud.md`. Реальный production-переход намеренно не выполнялся — `task.md` требует отдельного явного разрешения на эту операцию.

## Ограничения и принятые безопасные решения

- Это systemd stop/start provider с коротким перерывом доступности; blue/green и zero-downtime не заявляются.
- Схема приложения/БД не откатывается автоматически. Hooks требуют обратной совместимости и отдельно проверенного backup/restore.
- Все проекты используют общий build identity и общий deployment identity. Для взаимно недоверенных проектов нужны отдельные VM/экземпляры, а не только разные YAML.
- Произвольные symlink внутри исходников сборки и артефактов отвергаются. Mutable shared-ссылки добавляются контролируемо после проверки.
- GitHub App installation token поддерживается через секретный профиль; выпуск и ротация токенов выполняются внешним доверенным механизмом.
- Python build-venv не переносится в runtime; окружение запуска Python-приложения подготавливается отдельно. Node-публикация должна содержать нужный runtime payload; dist со статикой и standalone-приложение требуют своих корректных build-настроек.
- Политика approve фиксирует выбранный артефакт и актор операции, но не реализует независимое многостороннее согласование.
- Установщик менеджера сохраняет предыдущую версию. Восстановление запускается Bash-скриптом независимо от Python; обратная миграция будущих несовместимых схем БД потребует собственного плана.

Полная архитектура, схема, контракты артефактов, безопасность, установка, восстановление и примеры описаны в остальных документах этой папки.
