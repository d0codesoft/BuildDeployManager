# Configuration

Each `/etc/scdeploy/projects/*.yaml` defines one project. File names are arbitrary; `project.name` is the identity. Duplicate identities, overlapping application roots, duplicate YAML keys, unknown fields and wrong types are errors. Schema 1 uses strict dataclasses: strings do not coerce to booleans, and booleans do not coerce to integers. Error messages never echo field values.

Root must own project configuration and its directory. They must not be writable by group/other users. Use `root:scdeploy`, directory 0750 and files 0640. Arbitrary commands, hooks, trusted hosts and public keys are administrative permissions. `--dry-run` validates and describes a plan without making directories, opening SQLite, checking out code, downloading, sending notifications or invoking commands. It cannot prove remote availability or service readiness.

The complete machine-readable field inventory is generated in [schema reference](schema-reference.md). Examples are in `projects/examples/`.

`project`: required name; description, enabled and environment. Disabled projects are skipped by the timer. `production` defaults to manual approval through the global deployment policy.

`source`: type selects git/github/github-actions/github-release/http. Git requires repository and defaults branch to main; tag overrides branch. github repositories use owner/name; ordinary Git accepts HTTPS, SSH, deploy-key SCP syntax and local/file repositories for tests. No embedded HTTPS credentials. `auth_profile` references a protected JSON profile containing an installation/PAT token; SSH uses configured deploy keys or an agent with strict known-host verification. GitHub App short-lived installation tokens can be supplied by an external credential rotator. The manager does not store GitHub App private keys or mint tokens. Actions requires workflow and artifact_name; Releases requires an explicit tag and exact asset name. HTTP requires metadata_url and explicit trusted_hosts. `public_key` is the administrator-controlled Ed25519 PEM trust anchor. No trust-on-first-use or downloaded signing keys.

`build`: provider selects dotnet/node/python/command; configuration is Release/Debug; runtime is the artifact runtime identifier. .NET projects each have a relative path and distinct non-overlapping output. `restore`, `tests`, `self_contained` control corresponding tool phases. `nuget_config` is a repository-relative NuGet config; use an independently configured feed credential mechanism, never embed passwords in YAML. Node checks node_major against the installed executable; publishes publish_directory. Python uses python_executable, requirements, distribution and a build-only venv; publication contains deployable source or distributions, never a relocatable copied venv. Working_directory and all publication/project paths are relative, reject traversal/symlinks. commands/test_commands are lists of argv arrays, never shell strings. `environment` is an explicit public build environment, not a secret store. timeout_seconds bounds each command; resource limits CPU quota and memory use systemd scope properties. A missing resource manager fails the build. Global `--max-builds 1` disables concurrent builds; default 2. The supplied timer serializes check cycles.

`deploy`: releases and current must be siblings inside one dedicated application root. This deliberately excludes legacy links like /var/www/scloud pointing directly at /opt/scloud. Migrate explicitly. Services must end in .service; systemd preflight requires a non-root user and paths through current. observe_only defaults true. require_signature defaults true. Automatic rollback cannot be disabled. keep_releases retains at least two plus current/previous. `shared` maps relative payload links to pre-existing relative paths under `<application>/shared`; payload targets must be absent. `pre_deploy` contains administrator-reviewed argv hooks run unprivileged after verification and before service stops. Hooks must not mutate the signed payload; verification runs again. Database backup/migration scripts may perform external operations, so administrators must guarantee their backward compatibility.

`healthchecks`: HTTP verifies expected_status and optional body_contains (first 64 KiB); TCP verifies connection to host/port; systemd requires a service from this project's service list; command executes administrator-approved argv. Each has a total timeout_seconds, attempts and interval_seconds. Systemd process states are checked in addition to application readiness.

`updates`: manual/notify/automatic; check_interval is a positive duration like 30m. Automatic requires explicit allowed_branches, require_approval false and a maintenance window. Git/GitHub projects run the same local clone/build/publish/release pipeline, authenticated by a protected build record; remote artifact projects require signature verification and a signed source_branch. UTC window is start hour inclusive/end hour exclusive; overnight ranges are supported. max_failures suspends repeated failed automatic deployments; manually investigate and recover before resetting state. allow_downgrade defaults false for semantic release versions; explicit rollback is the preferred recovery path. Local opaque commit versions follow the selected upstream branch HEAD, including force-push changes. A successful branch build alone grants no production deployment permission without the administrative update policy.

`notifications`: email and telegram each have enabled, profile, on_success, on_failure. Configurations reference a secret profile only. See [examples](examples.md) for profile schemas. CLI directory overrides select alternate configuration, state, logs and credentials for testing; administrative OS permissions still apply.
